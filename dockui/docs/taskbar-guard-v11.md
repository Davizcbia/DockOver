# Taskbar Guard V0.11 — simulation-only integration

Production taskbar hiding remains **disabled**, even with `--hide-taskbar`. No shell window operations are reachable through the new guard. This is not a production recovery guard.

`LiquidDesktopManager --guard-sim-dir <new-empty-test-directory>` starts the same-build `docky-taskbar-guard-sim.exe` only after the managed Dock's first successful Present. A restricted inherited-handle list transfers real Manager and Dock process handles, an independent readiness event, a stop event, a fake hidden-state event, a shared mutex, and a duplicate of the Manager singleton mutex. The latter keeps the singleton name present until the guard exits, including after a Manager crash. Readiness and live-process checks precede the simulated transaction.

The test directory must already exist and the record must not exist. The Manager creates and flushes a Closed record with CREATE_NEW, saves a Pending journal under the shared mutex before setting the fake hidden event, and saves Hidden after it. On quit, Manager crash, Dock exit, or guard crash, the surviving participant calls the existing `RestoreTaskbarWindows` machinery with fake event operations. The guard process waits on inherited kernel process handles, not reusable process IDs. `--guard-sim-crash-after-hide` is an explicit test-only fault: it terminates **that Manager process** after the fake hide while holding the mutex, before the Hidden commit, to exercise abandoned-mutex recovery. It can leave that test Manager's Dock/Menu Bar processes alive; identify and close only the test's own children.

Focused end-to-end tests in this round launched the real Manager and Dock/Menu Bar, with records and Dock config in new temp directories. Normal quit, injected crash in the Pending-to-Hidden window, owned Dock exit, guard exit, duplicate Manager rejection, and explicit hide refusal passed. The independent `docky-taskbar-restore.exe` was checked against simulation records; its conservative CLI refuses Pending and is not integrated into the new simulation path. The guard reuses the same window-record restore library as that tool.

This is a protocol experiment, not permission to hide real windows: its identity is synthetic, the transaction mutex is per simulation session and there is no authenticated persistent production session, multi-monitor window ownership, Explorer recreation protocol, or proven manual recovery for simultaneous Manager/guard death and Pending records. No real shell visibility changes were tested. Complete these and fault-injection tests before considering a production guard; keep default and explicit hide disabled until independently verified and explicitly authorized for real-desktop testing.
